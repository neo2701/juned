# Requirements Document

## Introduction

Phase 3 of the JUNED E-Voting System implements the zk-SNARK Ballot Engine — the core cryptographic voting mechanism. This phase integrates Groth16 zero-knowledge proofs to enable voters to cast ballots that are verifiably valid without revealing voter identity. The system uses a Poseidon-based Merkle Tree of voter commitments, generates nullifiers to prevent double-voting, and performs client-side proof generation with server-side verification.

## Glossary

- **Ballot_Engine**: The subsystem responsible for generating, submitting, and verifying zero-knowledge proof-based votes
- **Vote_Circuit**: The circom circuit (`vote.circom`) that proves knowledge of a private key, Merkle Tree membership, and generates a nullifier
- **MerkleTreeService**: A PHP service that constructs and manages a Poseidon-based Merkle Tree of eligible voter commitments for a given election
- **Voter_Dashboard**: The Vue.js frontend component (`Voter/Dashboard.vue`) where authenticated voters cast their ballots
- **SuaraController**: The Laravel controller responsible for receiving vote submissions, verifying proofs, and persisting encrypted votes
- **Proof_Verifier**: A Node.js script (`verify.js`) that verifies Groth16 proofs using snarkjs and the verification key
- **Voter_Commitment**: A Poseidon hash of the voter's private key, stored in the `pemilih` table as `private_key_hash`
- **Nullifier_Hash**: A Poseidon hash of `(privateKey, pemiluId)` used to prevent double-voting without linking voter to ballot
- **Merkle_Proof**: The set of sibling hashes (path elements) and path indices required to prove a leaf's inclusion in the Merkle Tree
- **Trusted_Setup**: The ceremony that generates the proving key (`zkey`) and verification key (`vkey.json`) for the Groth16 proof system
- **Groth16_Proof**: A succinct non-interactive zero-knowledge proof generated by the voter's browser using snarkjs
- **Encrypted_Vote**: The voter's candidate selection (`kandidat_id`) encrypted before submission to prevent server-side ballot inspection

## Requirements

### Requirement 1: Merkle Tree Construction

**User Story:** As a KPU Admin, I want the system to build a Merkle Tree of all eligible voter commitments for an election, so that voters can prove their eligibility without revealing their identity.

#### Acceptance Criteria

1. WHEN a KPU Admin triggers Merkle Tree generation for an election, THE MerkleTreeService SHALL collect all voter commitments (the `private_key_hash` values) from the `pemilih` table and construct a Poseidon-based binary Merkle Tree with a depth of 10 levels, supporting a maximum of 1024 leaves.
2. IF fewer than 1024 voter commitments exist, THEN THE MerkleTreeService SHALL pad the remaining leaf positions with a zero-value leaf of `0` (the integer zero) until the tree contains exactly 1024 leaves.
3. IF more than 1024 voter commitments exist for the election, THEN THE MerkleTreeService SHALL reject the tree generation and return an error indicating the voter count exceeds the maximum tree capacity of 1024.
4. WHEN the Merkle Tree is successfully constructed, THE MerkleTreeService SHALL store the computed root hash in the `merkle_tree` table associated with the given `pemilu_id` and set the record's `status` field to `'GENERATED'`.
5. WHEN a voter requests their Merkle Proof, THE MerkleTreeService SHALL return an array of 10 path elements (sibling hashes) and an array of 10 binary path indices (each value being 0 or 1) corresponding to the voter's commitment leaf position.
6. IF a voter's commitment is not found in the Merkle Tree, THEN THE MerkleTreeService SHALL return an error indicating the voter is not eligible for the election, without revealing which commitments are present in the tree.

### Requirement 2: Trusted Setup and Circuit Compilation

**User Story:** As a system administrator, I want the zk-SNARK circuit compiled and the trusted setup completed, so that voters can generate proofs and the server can verify them.

#### Acceptance Criteria

1. THE Vote_Circuit SHALL accept private inputs (privateKey, pathElements[10], pathIndices[10]) and public inputs (root, pemiluId, kandidatId) and output nullifierHash as a public signal accessible in the proof's public signals array.
2. WHEN the circuit is compiled, THE Ballot_Engine SHALL produce a WASM witness generator (`vote.wasm`) and an R1CS constraint file (`vote.r1cs`) in the circuits output directory.
3. WHEN the trusted setup is executed, THE Ballot_Engine SHALL generate a proving key (`vote_final.zkey`) and a verification key (`vkey.json`) using the Groth16 protocol with the Powers of Tau ceremony file (`pot14_final.ptau`) of at least 2^14 constraints capacity.
4. THE Vote_Circuit SHALL compute the voter commitment as Poseidon(privateKey) and verify its inclusion in the Merkle Tree against the provided root using the pathElements and pathIndices inputs.
5. THE Vote_Circuit SHALL compute the nullifier as Poseidon(privateKey, pemiluId) and expose it as a public output signal.
6. THE Vote_Circuit SHALL bind the kandidatId to the proof via a constraint so that the proof is invalid if the kandidatId is altered after proof generation.
7. WHEN the trusted setup is complete, THE Ballot_Engine SHALL validate that a proof generated with the proving key (`vote_final.zkey`) is successfully verified by the verification key (`vkey.json`) using a test input before deployment.
8. IF the circuit compilation fails or the trusted setup ceremony file is missing, THEN THE Ballot_Engine SHALL terminate the process with a non-zero exit code and output an error message indicating the failure reason.

### Requirement 3: Client-Side Proof Generation

**User Story:** As a voter, I want to generate a zero-knowledge proof in my browser, so that I can prove my eligibility and cast my vote without revealing my private key.

#### Acceptance Criteria

1. WHEN a voter navigates to the Voter_Dashboard, THE Voter_Dashboard SHALL fetch the list of elections with status 'BERJALAN' and their associated candidates from the server and display them within 3 seconds of page load.
2. WHEN a voter selects a candidate and initiates voting, THE Voter_Dashboard SHALL prompt the voter to enter their private key via a password-masked input field.
3. WHEN the voter provides their private key, THE Voter_Dashboard SHALL validate that the key is a non-empty numeric string representing a valid finite field element before proceeding with proof generation.
4. WHEN the private key is validated, THE Voter_Dashboard SHALL fetch the current Merkle Tree data (all commitments and root) from the server and compute the Merkle Proof locally using the voter's commitment (Poseidon of privateKey) as the target leaf.
5. IF the Merkle Tree data fetch fails due to network error or non-200 response, THEN THE Voter_Dashboard SHALL display an error message indicating the tree data could not be retrieved and allow the voter to retry without re-entering the private key.
6. WHEN the Merkle Proof is computed, THE Voter_Dashboard SHALL display a loading indicator and generate a Groth16 proof using snarkjs with the WASM witness generator, the proving key, and the circuit inputs (privateKey, pathElements, pathIndices, root, pemiluId, kandidatId).
7. WHEN the proof is generated, THE Voter_Dashboard SHALL compute the nullifier hash locally using Poseidon(privateKey, pemiluId) and submit the proof JSON, nullifier hash, public signals, and kandidatId to the SuaraController.
8. WHEN the proof and nullifier hash have been submitted or proof generation fails, THE Voter_Dashboard SHALL clear the private key value from memory and from the input field.
9. IF proof generation fails, THEN THE Voter_Dashboard SHALL display an error message indicating the failure reason (e.g., invalid key, commitment not in tree, witness generation error) without including the private key value in any displayed output, console log, or network request.

### Requirement 4: Server-Side Proof Verification

**User Story:** As the system, I want to verify submitted zk-SNARK proofs on the server, so that only valid votes from eligible voters are recorded.

#### Acceptance Criteria

1. WHEN a vote submission is received, THE SuaraController SHALL validate that the request payload contains a non-empty proof JSON object, a public signals array with exactly 4 elements (root, pemiluId, kandidatId, nullifierHash), and an encrypted vote string, before invoking the Proof_Verifier.
2. IF the request payload is missing required fields or contains a malformed proof JSON, THEN THE SuaraController SHALL reject the vote and return an error response with status code 422 indicating which fields are invalid.
3. WHEN the request payload is valid, THE SuaraController SHALL invoke the Proof_Verifier with the proof JSON, public signals array, and the verification key (`vkey.json`) within 10 seconds.
4. WHEN the Proof_Verifier confirms the proof is valid, THE SuaraController SHALL check that the nullifier hash output in the public signals matches the nullifier hash value included in the submission payload.
5. IF the proof verification fails or the Proof_Verifier returns an error, THEN THE SuaraController SHALL reject the vote and return an error response with status code 422 indicating proof verification failure.
6. IF the nullifier hash already exists in the `nullifier` table for the given `pemilu_id`, THEN THE SuaraController SHALL reject the vote and return an error response with status code 409 indicating the voter has already voted.
7. WHEN the proof is valid and the nullifier is unique for the given `pemilu_id`, THE SuaraController SHALL store the encrypted vote in the `suara` table with status MASUK, store the nullifier hash in the `nullifier` table, and store the proof data in the `zkp_proof` table within a single database transaction.
8. IF the database transaction fails, THEN THE SuaraController SHALL roll back all changes and return an error response with status code 500 indicating the vote could not be recorded.

### Requirement 5: Double-Vote Prevention

**User Story:** As the system, I want to prevent any voter from casting more than one vote per election, so that election integrity is maintained.

#### Acceptance Criteria

1. WHEN a vote submission is received, THE SuaraController SHALL verify that no record with the same (pemilu_id, nullifier_hash) pair exists in the `nullifier` table before persisting the vote or nullifier record.
2. IF a duplicate nullifier is detected during the uniqueness check or a database unique-constraint violation occurs on the (pemilu_id, nullifier_hash) pair, THEN THE SuaraController SHALL reject the submission, return a 409 Conflict response with an error message indicating the voter has already voted in this election, and SHALL NOT persist any vote or proof data for that submission.
3. THE Vote_Circuit SHALL deterministically produce the same nullifier hash for the same (privateKey, pemiluId) combination regardless of the kandidatId or Merkle Proof path.
4. WHEN the SuaraController stores a nullifier_hash, THE SuaraController SHALL store it as the decimal string representation of the circuit's Poseidon output field element, matching the format produced by the client-side snarkjs public signals array.

### Requirement 6: Vote Encryption

**User Story:** As a voter, I want my candidate selection to be encrypted before submission, so that the server cannot inspect individual ballot choices in plaintext.

#### Acceptance Criteria

1. WHEN the voter submits a vote, THE Voter_Dashboard SHALL encrypt the kandidatId using a Poseidon hash commitment of the form Poseidon(kandidatId, randomSecret) and include the resulting ciphertext in the submission payload as the `encrypted_vote` field.
2. THE Voter_Dashboard SHALL pass the plaintext kandidatId as the public input to the zk-SNARK circuit for proof generation, and store only the encrypted form (Poseidon commitment) in the `suara` table, so that the proof binds the candidate choice via the circuit's public input constraint while the persisted record remains unreadable without the randomSecret.
3. WHEN the proof is valid and the vote is persisted, THE SuaraController SHALL store the encrypted_vote value in the `suara` table with status 'MASUK' and SHALL NOT log or persist the plaintext kandidatId.
4. IF the encrypted vote cannot be decrypted by the designated tallying authority during the tally phase, THEN THE Ballot_Engine SHALL update the vote record status to 'DITOLAK' in the `suara` table and exclude that record from the final vote count.
5. IF the Voter_Dashboard fails to generate the encryption commitment before submission, THEN THE Voter_Dashboard SHALL block the submission and display an error message indicating that vote encryption failed.

### Requirement 7: Merkle Tree API Endpoint

**User Story:** As a voter's browser, I want to fetch the Merkle Tree data for an election, so that I can compute my inclusion proof locally.

#### Acceptance Criteria

1. WHEN an authenticated voter requests the Merkle Tree data for an election, THE Ballot_Engine SHALL return a JSON response containing the ordered list of all leaf commitment hashes (in their tree-position order from index 0 to 2^10 - 1) and the current Merkle root hash.
2. IF the requested election does not have status 'BERJALAN', THEN THE Ballot_Engine SHALL reject the request and return a 403 response with a message indicating the election is not in an active voting state.
3. IF the Merkle Tree has not been generated for the requested election, THEN THE Ballot_Engine SHALL return a 404 response with a message indicating the Merkle Tree is not yet available for the election.
4. IF the requested election ID does not exist, THEN THE Ballot_Engine SHALL return a 404 response.
5. THE Ballot_Engine SHALL return the Merkle Tree data within 2 seconds for a tree containing up to 1024 leaf commitments.

### Requirement 8: Verification Key and WASM Asset Serving

**User Story:** As a voter's browser, I want to download the proving key and WASM witness generator, so that I can generate proofs client-side.

#### Acceptance Criteria

1. THE Ballot_Engine SHALL serve the WASM witness generator file (`vote.wasm`) as a static asset accessible without authentication, with Content-Type `application/wasm`.
2. THE Ballot_Engine SHALL serve the proving key file (`vote_final.zkey`) as a static asset accessible without authentication, with Content-Type `application/octet-stream`.
3. THE Ballot_Engine SHALL serve the verification key file (`vkey.json`) as a static asset accessible without authentication, with Content-Type `application/json`.
4. IF any of the asset files (`vote.wasm`, `vote_final.zkey`, `vkey.json`) is not found on the server, THEN THE Ballot_Engine SHALL return a 404 response.
5. WHEN a client requests an asset file, THE Ballot_Engine SHALL return the complete file content within 30 seconds for files up to 50 MB in size.

### Requirement 9: Voter Eligibility Validation

**User Story:** As the system, I want to validate that a voter is eligible before allowing proof generation, so that ineligible voters cannot waste resources attempting to vote.

#### Acceptance Criteria

1. WHEN a voter provides their private key and initiates voting, THE Voter_Dashboard SHALL compute the voter's commitment using Poseidon(privateKey) and verify that this commitment exists in the fetched Merkle Tree leaves before attempting proof generation.
2. IF the voter's commitment is not found in the Merkle Tree leaves, THEN THE Voter_Dashboard SHALL display an error message indicating the voter is not registered for the election and SHALL NOT proceed with proof generation.
3. WHILE an election status is not 'BERJALAN', THE Voter_Dashboard SHALL disable all vote-submission controls and display the current election status to the voter.
4. IF the Merkle Tree data fetch fails or returns an empty leaf set, THEN THE Voter_Dashboard SHALL display an error message indicating that eligibility cannot be verified and SHALL NOT proceed with proof generation.

### Requirement 10: Proof Verifier Script

**User Story:** As the server, I want a standalone verification script that can be invoked to validate Groth16 proofs, so that Laravel can delegate cryptographic verification to a Node.js process.

#### Acceptance Criteria

1. THE Proof_Verifier SHALL read a single JSON object from stdin containing three fields: `proof` (the Groth16 proof object), `publicSignals` (an array of 4 string elements representing root, pemiluId, kandidatId, and nullifierHash), and `vkeyPath` (a string file path to the verification key JSON file).
2. WHEN invoked with valid inputs, THE Proof_Verifier SHALL write to stdout a JSON object containing a `valid` boolean field indicating whether the proof is valid, and exit with code 0.
3. IF the Proof_Verifier receives input that is not valid JSON or is missing required fields (`proof`, `publicSignals`, or `vkeyPath`), THEN THE Proof_Verifier SHALL exit with a non-zero exit code and write to stdout a JSON object containing an `error` field with a message indicating the nature of the malformed input.
4. IF the verification key file specified by `vkeyPath` does not exist or is not readable, THEN THE Proof_Verifier SHALL exit with a non-zero exit code and write to stdout a JSON object containing an `error` field indicating the verification key file could not be loaded.
5. THE Proof_Verifier SHALL produce the same `valid` result when invoked multiple times with identical proof, publicSignals, and verification key inputs.
6. THE Proof_Verifier SHALL complete execution and produce output within 30 seconds of invocation.
